# Edge contract v1

This document specifies the HTTP interface between the bridge and the Convex app. The bridge is
the Go service in `bridge/`; it speaks IMAP and SMTP submission to mail clients and holds no
data. The edge is the set of HTTP routes this package (`@nordwerk/convex-mail-bridge`) mounts on
the app's `*.convex.site` URL; the data behind them lives in Convex. If you write a different
bridge, or a different edge, this is the specification to build against.

The limits and error texts below are the ones in `src/client/edge.ts` (`BRIDGE_LIMITS`,
`ERROR_TEXT`, `SUBMIT_REJECTIONS`, `DEFAULT_FOLDER_NAMES`). The Go bridge uses the same numbers
(`bridge/internal/edge/limits.go`). A change to a number is made here first and then in both
places.

Revision 1.2 (more folders than `INBOX` and `Sent`) is work in progress. It is described in its
own section at the end. The Go bridge in this repository implements version 1: two folders.

Terms used in this document:

| Term | Meaning |
| --- | --- |
| mailbox | what one mail account of the app owns; identified at the edge by an opaque key |
| ledger | the per-mailbox record in Convex of UIDs, flags, change counters and tombstones |
| session token | a secret the edge issues at `/login`; it stands for one authenticated connection |
| device password | a password for one mailbox that a mail client types in; only its hash is stored |
| mirror | the bridge's in-memory copy of the folder rows (UID, flags, size, date) |
| tombstone | a ledger row that marks a message as hidden from mail clients |

## Overview

- Base URL: `${CONVEX_SITE_URL}/bridge/v1`, where `CONVEX_SITE_URL` is
  `https://<deployment>.convex.site`. Every call is `POST`. Request and response bodies are JSON
  (UTF-8) unless a route says otherwise (`/raw` answers with a raw message, `/submit` takes one).
- Every call carries `Authorization: Bearer <MAIL_BRIDGE_SECRET>`. The secret is shared between
  the bridge and the Convex deployment. It must be at least 32 characters long (after trimming);
  with a shorter or missing secret the edge is off and answers every route with `401` and an
  empty body. A missing or wrong secret is answered the same way, before any other processing.
- Every call except `login` and `seq` also carries `X-Bridge-Session: <session token>`. The
  mailbox follows from the session token only; no route takes a mailbox from the request body.
  A token that is unknown, expired, whose device password was revoked, or whose mailbox is
  switched off gets `401 {"error":"session"}`. The bridge then ends that one connection.
- Error shape: `{"error":"<code>","message":"<short text>"}`, plus extra fields where a route
  says so. The text never contains addresses or message content. Errors the edge did not
  foresee are `500`; the bridge then answers the mail client `NO [UNAVAILABLE]` (IMAP) or `451`
  (SMTP) and does not retry by itself.
- Timeouts on the bridge side, per call: 15 s; 60 s for `raw` and `submit`. They can be changed
  with `EDGE_TIMEOUT_MS` and `EDGE_LONG_TIMEOUT_MS`.
- Types: `uid`, `modseq`, `uidValidity`, `uidNext` and `highestModseq` are integers.
  `internalDate` is milliseconds since 1970. `expiresAt` is milliseconds since 1970.
  Flags are strings as in IMAP (`\Seen`, `\Flagged`, `$Forwarded`, ...), sorted and unique.
- Folders: every mailbox has exactly `INBOX` and `Sent`. Revision 1.2 can add more (see the end).
- Session tokens are 43 characters (256 bit as base64url). Device passwords generated by the
  package are a prefix (default `mb_`) and 39 characters of lowercase base32 (192 bit).

### Error codes

| `error` | HTTP | `message` | Used for |
| --- | --- | --- | --- |
| `auth` | 401 | Sign-in failed. | `/login`: unknown address, wrong password, revoked device |
| `throttled` | 429 | Too many failed attempts, try again later. | `/login`; adds `retryAfterSeconds` |
| `preparing` | 503 | The mailbox is being prepared. | `/login` while the mailbox cannot be used yet |
| `session` | 401 | Session invalid or expired. | every route with `X-Bridge-Session` |
| `folder` | 404 or 403 | Folder unknown or not allowed here. | unknown folder (404); `/append` outside `Sent` (403) |
| `gone` | 404 | Message no longer exists. | `/raw` |
| `uidvalidity` | 409 | The folder was renumbered, read it again. | `/raw` |
| `resync` | 410 | State too old, read the folder again. | `/changes` |
| `unknown` | 409 | Message unknown. | `/append` |
| `request` | 400 | Invalid request. | unknown field, wrong type, value out of range |
| `too_large` | 413 | Request too large. | JSON body over 64 KiB |
| `internal` | 500 | Internal error. | anything unforeseen |

Rejections of `/submit` use their own codes and carry an `smtpCode`; see "Submission".

### Example

```sh
curl -sS -X POST "https://<deployment>.convex.site/bridge/v1/login" \
  -H "Authorization: Bearer $MAIL_BRIDGE_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"address":"user@example.com","password":"<device password>","clientIp":"192.0.2.10"}'
```

```json
{ "session": "<43 characters>", "expiresAt": 1790000000000, "mailbox": "<opaque mailbox key>" }
```

```sh
curl -sS -X POST "https://<deployment>.convex.site/bridge/v1/entries" \
  -H "Authorization: Bearer $MAIL_BRIDGE_SECRET" \
  -H "X-Bridge-Session: <session token>" \
  -H "Content-Type: application/json" \
  -d '{"folder":"INBOX","limit":500}'
```

## Routes

All routes are `POST` below `/bridge/v1`. Optional request fields are marked with `?`.

| Path | Request | Response `200` |
| --- | --- | --- |
| `/login` | `{"address","password","clientIp","bridge"?}` | `{"session","expiresAt","mailbox"}` |
| `/folders` | `{}` | `{"folders":[Folder, ...]}` |
| `/entries` | `{"folder","afterUid"?,"limit"}` | `{"rows":[Row, ...],"more","uidValidity",...}` |
| `/changes` | `{"folder","sinceModseq","limit"}` | `{"rows":[ChangedRow, ...],"more",...}` |
| `/raw` | `{"folder","uid","uidValidity"}` | the raw message (`message/rfc822`) |
| `/store` | `{"folder","uids","add"?,"remove"?}` | `{"rows":[{"uid","flags","modseq"}, ...]}` |
| `/expunge` | `{"folder","uids"}` | `{"uids":[...]}` |
| `/append` | `{"folder":"Sent","messageId","digest"}` | `{"uid","uidValidity"}` |
| `/seq` | `{"sessions":[...]}` | `{"results":[{"ok":true,"seq":n} or {"ok":false}, ...]}` |
| `/submit` | the raw message; envelope in headers | `{"status":"sent","uid"?}` or `{"status":"unknown"}` |

Shapes used above:

- `Folder` = `{"name","specialUse"?,"uidValidity","uidNext","highestModseq","exists","unseen"}`
- `Row` = `{"uid","flags","modseq","size","internalDate"}`
- `ChangedRow` = `Row` plus `"live"` (`false` marks a row that left the folder)
- `/entries` and `/changes` answer `{"rows","more","uidValidity","uidNext","highestModseq"}`

### `/login`

- Request: `address` (at most 320 characters), `password` (at most 256), `clientIp` (a bare IPv4
  or IPv6 address, at most 64 characters, no port, brackets or zone). The edge lowercases and
  trims the address. `bridge` is the bridge version, an integer from 1 to 1000; a missing field
  means 1 (see "Revision 1.2").
- Response: `session` is the session token. `expiresAt` is when it ends. `mailbox` is a stable,
  opaque key of the mailbox. The bridge keys its mirror and its raw message cache on it.
- Other responses: `401 auth` (unknown address, wrong password and revoked device password are
  indistinguishable), `429 throttled` with `retryAfterSeconds` and a `Retry-After` header,
  `503 preparing` (a backfill is running, or the mailbox is not ready for this bridge version).
- The edge counts failed attempts per pair of address and client IP, and per client IP. Keys are
  hashed with the shared secret, so the database holds neither addresses nor IPs. IPv6 addresses
  are counted by their /64 prefix; an IPv4 address wrapped in IPv6 (`::ffff:192.0.2.1`) counts as
  IPv4. A valid device password is never throttled: `429` is only for invalid attempts over the
  limit.

### `/folders`

Returns the folders of the mailbox with their counters. For a mailbox on version 1 these are
`INBOX` and `Sent`; `Sent` carries `specialUse` `\Sent`. `exists` and `unseen` are counts,
`uidNext` the next UID to be assigned, `highestModseq` the highest change state of the folder.

### `/entries`

Reads a folder page by page. `limit` is 1 to 2000. With `afterUid` (0 or more, absent or `null`
for the first page) the edge returns the live rows with a larger UID. Rows are sorted by `uid`,
ascending; `more` says whether another page follows. Deleted (hidden) rows are not listed.
An unknown folder gives `404 {"error":"folder"}`.

### `/changes`

Returns the rows that changed after `sinceModseq`, sorted by `modseq` ascending, each row at most
once, with `live: false` for rows that left the folder. `limit` is 1 to 2000. The edge keeps
removed rows for a limited time. If `sinceModseq` is older than that, or higher than the highest
state the folder has ever had, the answer is `410 {"error":"resync"}`: the bridge drops its
mirror of the folder and reads it again with `/entries`. An unknown folder gives `404 folder`.

### `/raw`

Returns one message. `uidValidity` is the folder identifier the bridge learned the UID under.
The response body is the raw message (RFC 822 bytes) with `Content-Type: message/rfc822` and a
`Content-Length`. Other responses: `404 gone` (also for an unknown folder), and
`409 uidvalidity` if the folder's identifier no longer matches: the bridge drops its mirror.

### `/store`

Adds and removes flags. `uids` has at most 500 entries; `add` and `remove` have at most 64 flags
each, 100 characters per flag, and may be missing or `null`. The response lists only the rows
that actually changed, with their full flag set and new `modseq`.

- When the request names `\Seen` in `add` or `remove`, the edge hands every row the request named,
  with the state it has now, to the app's `onSeen` callback, inside the same mutation that
  updates the ledger. Either both are written or neither.
- The edge processes the UIDs in batches of `storeBatch` per mutation; the default is 10 and the
  app can configure it. If the session ends between two batches, the earlier batches stay
  written and the answer is `401 session`. The bridge ends the connection; the mail client
  reconciles the flags the next time it connects.
- Unknown folder: `404 folder`.

### `/expunge`

Hides messages from mail clients. `uids` has at most 500 entries. The response lists the UIDs
that were actually hidden.

- The edge sets a tombstone in the ledger. The messages disappear from the folder for mail
  clients; the app's own data is not deleted by the package.
- The app may react through an optional `onExpunge` callback.
- Unknown folder: `404 folder`.

### `/append`

Answers the question a mail client asks when it files a message in `Sent` after sending it
(IMAP `APPEND`): is this a message that was sent through us?

- `folder` must be the folder with special use `\Sent`; anything else is `403 {"error":"folder"}`.
- `messageId` is the `Message-ID` header value, with or without angle brackets; the edge
  normalizes it (angle brackets and white space removed). At most 1000 characters as sent and
  500 after normalizing.
- `digest` is the SHA-256 of the raw bytes as 64 hex characters. The edge checks only its shape;
  it is not compared with anything.
- The edge asks the app's `findSent` callback for the message with that Message-ID. If it exists,
  the answer is `{"uid","uidValidity"}` of that message in `Sent`. If it does not, or if the app
  registered no `findSent` callback, the answer is `409 {"error":"unknown"}`. The bridge tells
  the mail client `NO [CANNOT]`.

### `/seq`

Asks for the change counters of the mailboxes behind up to 200 session tokens.

- The request carries the shared secret only, no session header. It may include the tokens of
  open SMTP connections.
- `results` has one entry per token, in the same order. `{"ok":true,"seq":n}` gives the change
  counter of the token's mailbox; `{"ok":false}` means the token is invalid (an entry that does
  not have the shape of a token is answered the same way). The bridge ends the connections of
  invalid tokens.
- The bridge compares the counter with the last value it saw for that mailbox; see "Rules for
  the bridge".

### `/submit`

Hands over a message the mail client sent through SMTP submission. See "Submission".

## Rules for the bridge

- The bridge calls `login` once per IMAP connection and once per SMTP connection. The session
  token lives in the memory of that connection; it is never written to disk and never logged.
  When it expires, the connection ends.
- The bridge polls `seq` every 2 seconds, for all open connections together, and only while
  connections are open. When the counter of a mailbox changed, it fetches `changes` for the
  folders that some connection of that mailbox has open.
- The mirror and the raw message cache belong to one mailbox and one `uidValidity`. A connection
  reads from them only after its own successful login, and never across mailboxes.
- `clientIp` comes from the PROXY protocol header of the connection (v1 or v2). In operation,
  connections without a valid PROXY header are rejected; this can be turned off for local use
  (`PROXY_PROTOCOL=off`).

## Strictness

- The edge rejects a body that has a field it does not know with `400 {"error":"request"}`. It
  also rejects wrong types and values out of range with `400 request`. The bridge sends exactly
  the fields in the table above.
- A JSON body over 64 KiB (65 536 bytes) is answered with `413 {"error":"too_large"}`. The edge
  reads at most that much; it does not buffer an unbounded body.
- The body is read only after the secret has been checked.
- Unknown folder: `/entries`, `/changes`, `/store` and `/expunge` answer `404 {"error":"folder"}`;
  `/raw` answers `404 gone`. A folder name that is not in `/folders` is unknown.
- `/changes` answers `410 resync` also when `sinceModseq` is higher than the folder's own state
  (the folder was reset on the edge side).
- Every error body carries `message`. `429` additionally carries the `Retry-After` header.
- A valid device password is never throttled.
- If the data of a mailbox no longer belongs to the mailbox's current owner (the mailbox was
  transferred), the bridge is off for that mailbox: `/login` answers `auth`, every session is
  invalid.

## Field limits

The edge answers anything above these limits with `400 request`. The Go bridge knows the same
numbers and answers such input itself (a failed login, `NO [CANNOT]`) instead of producing a
`400` that would look like a fault between bridge and edge.

| Field | Limit |
| --- | --- |
| JSON request body | 64 KiB |
| `address` (`/login`) | 320 characters |
| `password` (`/login`) | 256 characters |
| `clientIp` (`/login`) | 64 characters, bare IPv4 or IPv6 address without zone |
| `bridge` (`/login`) | integer, 1 to 1000 |
| `folder` | 64 characters |
| `limit` (`/entries`, `/changes`) | 1 to 2000 |
| `uids` (`/store`, `/expunge`) | at most 500 per call |
| flags in `add` / `remove` | at most 64 per list, 100 characters each |
| `messageId` (`/append`) | 1000 characters as sent, 500 without angle brackets |
| `sessions` (`/seq`) | at most 200 per call |
| session token | the edge issues 43 characters; the bridge accepts up to 256 |
| `uid`, `uidValidity` | integers from 1 to 2^32 - 1 (`afterUid`: from 0) |
| `sinceModseq` | integer from 0 to 2^53 - 1 |
| `/submit` body | 5 MiB (5 242 880 bytes) |
| `X-Envelope-From` | one address, at most 320 characters |
| `X-Envelope-To` | JSON list of 1 to 1000 addresses, at most 320 characters each |

Characters are counted as in JavaScript (UTF-16 code units).

## Submission

`POST /bridge/v1/submit` carries the raw message as the body with `Content-Type: message/rfc822`
and these headers:

| Header | Content |
| --- | --- |
| `X-Bridge-Session` | the session token of the SMTP connection |
| `X-Envelope-From` | the envelope sender, one address |
| `X-Envelope-To` | the envelope recipients as a JSON list of addresses |

What the edge does:

1. It checks the secret and the session.
2. It reads the body, at most 5 MiB. A larger body gets
   `413 {"error":"size","smtpCode":552,"message":"..."}`.
3. It passes the envelope and the raw bytes to the app's `submit` callback. The callback sends
   the message with whatever provider the app uses. The package does not send anything itself.
4. If the app registered no `submit` callback, the edge answers `503` with error `unavailable`
   and `smtpCode` 451.

Making a retry idempotent is the job of the app's `submit` callback. A mail client retries when
the connection drops, and the bridge itself answers `451` when the edge does not answer in
time (60 s) or answers with something unusable, so the same message can arrive twice.

Rate limiting of submissions is not part of the package. The app does it, optionally through an
`allowSubmit` callback; a refusal is answered as `limit` (see below).

### Results

| Response | Meaning for SMTP |
| --- | --- |
| `200 {"status":"sent","uid"?}` | `250`. `uid` is the UID of the message in `Sent`; it is absent if no UID could be assigned |
| `200 {"status":"unknown"}` | `250`. The outcome is not certain and is not treated as a failure |
| a rejection (below) | the `smtpCode` of the body, with the `message` text |
| `400 {"error":"request"}` without `smtpCode` | a fault of the bridge (missing or unreadable envelope headers); the bridge answers `451` |
| `500`, a timeout, an unreadable body | the bridge answers `451` and does not retry |

### Rejections

A rejection is `{"error","smtpCode","message"}`. The bridge passes `smtpCode` and `message` on
to the mail client. `message` is plain ASCII, at most 200 characters; the edge replaces every
other character with `?`, and the bridge does so again. A rejection never has HTTP status `500`.
These are exactly the nine rejections the edge knows:

| `error` | HTTP | `smtpCode` | Default `message` |
| --- | --- | --- | --- |
| `sender` | 422 | 550 | The sender must be the address of this mailbox. |
| `recipients` | 422 | 550 | The recipients of the envelope do not match To and Cc. |
| `content` | 422 | 554 | The message cannot be read. |
| `size` | 413 | 552 | The message is too large. |
| `conflict` | 409 | 550 | A different message with this Message-ID was already submitted. |
| `busy` | 409 | 451 | This message is still being sent. |
| `limit` | 429 | 451 | Too many messages, try again later. |
| `rejected` | 422 | 550 | The message was rejected. |
| `unavailable` | 503 | 451 | Sending is unavailable, try again later. |

How an app would typically use them:

- `sender`: the envelope sender or the `From` header is not the address of the mailbox.
- `recipients`: the envelope recipients differ from `To` plus `Cc` (a Bcc recipient is in the
  envelope only), there is no `To`, or there are more than 50 recipients.
- `content`: the message cannot be parsed, has no subject, or is signed or encrypted.
- `size`: the raw message is over 5 MiB, or the provider says it is too large.
- `conflict` and `busy`: the same `Message-ID` is submitted again with different content, or
  while the first submission is still running.
- `limit`: the app's own rate limit, or the provider's.
- `rejected`: the provider rejects the message for good (a sender domain that is not allowed, a
  blocked recipient).
- `unavailable`: temporary, for example no way to send is configured.

## Revision 1.2: folders (in progress)

This revision is not finished and may change. The Go bridge in this repository implements
version 1 and does not use anything below.

### What exists

- `/login` accepts the field `bridge` (integer 1 to 1000, default 1).
- A mailbox can hold more folders than `INBOX` and `Sent`: `Archive`, `Trash` and `Later`.
  Such a mailbox is called "a mailbox with folders". It is switched over explicitly, per
  mailbox (the app calls `addFolders`). A mailbox without folders behaves exactly as in version
  1, also for a newer bridge.
- A mailbox with folders only accepts `bridge` of 2 or more. An older bridge gets
  `503 {"error":"preparing"}` (for the mail client: temporarily unavailable). That is not a
  failed attempt, issues no session and does not count the device as used. The password and the
  throttle are checked first, as always: a wrong password stays `401 auth`. The reason is that an
  older bridge would send "delete" in the inbox as `/expunge`, which in a mailbox with folders
  is meant to do more than hide the message (see "Planned").
- `/folders`, `/entries`, `/changes`, `/raw` and `/store` work for every listed folder. A name
  that is not listed gives `404 folder`, as before.
- While the app has marked a mailbox as being prepared (a backfill is running), `/login` answers
  `503 preparing` and every session of that mailbox is invalid (`401 session`). The bridge ends the
  connections, the mail client signs in again and reads the folders again. A session from before
  a backfill stays invalid for good (also in `/seq`: `ok: false`). The `uidValidity` of `INBOX`
  and `Sent` does not change.

### Folders

`/folders` returns what the mailbox holds. The order has no meaning. The names are configurable
at the edge; the defaults are:

| `name` | `specialUse` | Role |
| --- | --- | --- |
| `INBOX` | none | the inbox |
| `Sent` | `\Sent` | sent messages |
| `Archive` | `\Archive` | archived messages |
| `Trash` | `\Trash` | messages in the trash |
| `Later` | none | messages set aside for later |

Which messages appear in which folder is up to the app.

The bridge takes the list as it comes. It knows two fixed things: `INBOX`, and the folder with
special use `\Sent` as the only target of `/append`. The edge compares folder names after
Unicode normalization (NFC), because a mail client may send an umlaut composed or decomposed.
`name` is UTF-8; encoding it for the mail client (modified UTF-7) is the bridge's job.

### Planned, may change

Both of the following are not built yet. A request to `/move` gets `404` without a JSON body.

**`/move`**: `{"folder","uids","target"}`, at most 100 UIDs, `target` like `folder` (64
characters). Response `200 {"moved":[{"uid","newUid"}],"uidValidity"}`. `uidValidity` and
`newUid` are valid in the target folder. Only UIDs that were actually moved are listed; unknown
ones are missing. The bridge answers the mail client with `COPYUID` for these pairs. Other
changes that follow from the move arrive as ordinary changes (`/changes`). The app decides what
a move means.

| Move | Effect | Response |
| --- | --- | --- |
| received message to `Archive`, `Trash` or `INBOX` | the app decides | `200` |
| sent message from `Sent` to `Trash` | hidden from mail clients | `200` with `moved: []` for that UID |
| anything to `Later`, anything to `Sent`, sent message to `Archive` or `INBOX` | none | `409 {"error":"cannot"}`, the bridge says `NO [CANNOT]` |
| source equals target | none | `200` with `moved: []` |
| mailbox without folders | none | `404 folder` |

- The `409 cannot` row is provisional until it has been tried with real mail clients. The whole
  request is rejected and nothing is moved.
- If a request names a UID that has meanwhile left the folder (the change was faster than the
  request), the edge treats it as the live row of that message. If the message is already in
  the target, it is listed in `moved` with its number there.

**`/expunge` in a mailbox with folders**, per folder:

| Folder | Effect |
| --- | --- |
| `INBOX`, `Archive`, `Later` | like `/move` to `Trash`; the response lists the UIDs that left the folder |
| `Sent`, `Trash` | as in version 1: hidden from mail clients only |

At most 100 UIDs per `/expunge` in `INBOX`, `Archive` and `Later` (the bridge splits larger
requests), otherwise 500. Until this is built, `/expunge` in those folders of a mailbox with
folders answers `{"uids":[]}` and does nothing.

**`/append`** stays as it is (only `Sent`). If the sent message lies in `Trash`, the edge answers
`200 {}` without a UID (this part exists already). The bridge then answers `OK` without
`APPENDUID`. An unknown message stays `409 unknown`.

Drafts and search (`/search`) are not part of this revision.

### Rolling out

Deploy the Convex side first, then the bridge. An edge that predates the `bridge` field rejects
it with `400 request`.

## Versioning

The path carries the major version: `/bridge/v1`. Changes inside a major version are additive:
new optional fields, new routes. They are announced through the `bridge` field in `/login`,
which tells the edge which revision the bridge can handle.
